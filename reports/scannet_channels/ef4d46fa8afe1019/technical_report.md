# B15 Hidden State 通道筛选实验报告

日期：2026-09-10\
实验编号：`ef4d46fa8afe1019`\
原始 B15 基线实验：`07c02b354a694662`\
当前主候选：**逐档筛选保留 384 维**；256 维保留为更高压缩率的对照。

## 1. 实验结论

本实验检验：完整 B15 hidden state 的 1536 个通道，是否可以通过筛选大幅减少，同时维持或改善三维对应匹配质量。

五场景留一验证的结果支持这个方向。**逐档筛选到 384 维后，体素命中率为 31.826%，10cm 命中率为 47.118%，平均三维误差为 0.2518 m。** 相对原始 1536 维，通道数减少 75%，体素命中率提高 2.915 个百分点，10cm 命中率提高 3.685 个百分点，平均三维误差降低约 24.20 mm，即 8.77%。这三项改善在五个留出场景中均成立。

筛选过程影响很大：在相同 384 维下，一次性排序截取、随机子集、PCA 的体素命中率分别为 26.609%、27.231%、27.559%，均低于原始特征的 28.912%。逐档重新评估通道组合，才能在本轮实验中保住并提高检索质量。

384 维是当前质量与维度之间的主候选，不是所有指标的唯一最优点：256 维的体素命中率最高，512 维的平均三维误差最低。384 维的 10cm 命中率最高，平均误差又非常接近 512 维。具体取舍见第 6 节。

**结论范围：** 本次验证的是“用训练场景筛通道，再应用到留出场景”的流程。五折分别产生不同通道列表；尚未完成一份用全部五场景拟合的固定通道表在额外场景上的验证。

## 2. 实验对象与数据

### 2.1 B15 hidden state 是什么

B15 指 `transformer.blocks[15]`，按 Python 从 0 编号。提取位置是完整 block 的输出，已经包含 block 内注意力、FFN 和残差的处理。

本次设置下的特征形状为：

```text
block 输出 token 序列       [B, 1560, 1536]
恢复空间网格                [B, 1536, 30, 52]
float32 自适应平均池化       [B, 1536, 14, 14]
选取 384 个原始通道         [B, 384, 14, 14]
检索时每个 token 的描述子    384 维，重新做 L2 归一化
```

池化只减少空间网格，不改变 1536 个通道。本实验直接选择其中的原始通道，保持 14×14 网格不变；384 维对应 384 个被保留的通道，不是 384 个 PCA 主成分，也不对应若干完整 attention heads。

每个场景缓存的形状是 `[32, 1536, 14, 14]`。这里第一维是 32 张采样帧的集合，原始提取采用单帧独立推理、`batch_size=1`，并非一次联合编码 32 帧视频。

实现位置：[extract.py 的 block hook][extract-code]。

## 3. 技术实现

### 3.1 用删除一个通道后的变化衡量重要性

设当前保留通道集合为 `S`，`H(S)` 是训练场景上的体素命中率，按“帧对等权，再场景等权”计算。对 `S` 内每个通道 `c`，分别计算：

```text
I_hit(c | S) = H(S) - H(S 去掉 c)
```

- `I_hit > 0`：删除后命中率下降，该通道对当前组合有帮助。
- `I_hit < 0`：删除后命中率上升，该通道在当前组合中可能产生干扰。
- `I_hit = 0`：单次删除没有改变该统计量，需要用副指标排序。

这里评估的是保留其他通道后，删除这一维的边际影响。每个候选都重新计算余弦相似度和 top-1 匹配，不使用单独一维的余弦相似度作为通道能力分数。

命中率是离散指标，因此排序还使用匹配间隔作为副指标。对每个可评价查询：

```text
margin = 最高的同体素候选余弦 - 最高的异体素候选余弦
I_margin(c | S) = M(S) - M(S 去掉 c)
```

`M` 使用相同的查询、帧对和场景聚合方式。若查询没有异体素候选，其 margin 贡献按零处理。最终按以下字典序保留通道：先按 `I_hit` 从大到小，再按 `I_margin` 从大到小，最后按原始通道编号从小到大稳定排序。没有将这些指标混合成一个加权总分。

**排序的主要目标一直是体素命中率。** 本轮没有把目标改成 10cm 命中率；384 维是在扫描结果中依据多项几何指标选出的折中候选。排序用的 `margin` 与报告中的 `similarity_gap` 定义不同，后者见第 4 节。

这是使用训练场景几何对应监督的离线特征选择。它不需要反向传播，也不更新 Wan 参数，但不是完全无监督的压缩方法。

### 3.2 批量消融如何加速

对两个当前特征向量 `x[S]`、`y[S]`，先计算完整内积和平方范数：

```text
d = sum(x[s] * y[s] for s in S)
a = sum(x[s] ** 2 for s in S)
b = sum(y[s] ** 2 for s in S)

删除通道 c 后：
d_c = d - x[c] * y[c]
a_c = max(a - x[c] ** 2, 0)
b_c = max(b - y[c] ** 2, 0)

cosine_c = d_c / (max(sqrt(a_c), 1e-12) * max(sqrt(b_c), 1e-12))
```

将这组运算广播到“待删除通道 × 源 token × 目标 token”，就能批量得到删除各个通道后的匹配分数。本次每批处理 64 个待删除通道，避免同时分配全部 1536 个候选的相似度矩阵。

加速筛选使用 PyTorch float64，以减少内积和范数做减法时的精度损失；最终所有候选的正式评分仍调用原有 NumPy float32 `evaluate_pair`。数学上的删除公式一致，但训练诊断分数与最终评分不能视为逐位相同的数值实现。

实现位置：[channel_selection.py][selection-code] 中的 `pair_ablation`、`scene_ablation`、`retrieval_values` 和 `rank_channels`。

### 3.3 逐档剪枝与一次性排序

一次性排序 `ablation_once`：在完整 1536 维上计算一次重要性，然后分别取前 K 个通道。

逐档剪枝 `ablation_iterative`：每删到一档维度，就在剩余通道内重新计算删除效果。完整实验路径为：

```text
1536 -> 1024 -> 768 -> 512 -> 384 -> 256 -> 128
```

简化过程如下：

```text
对每一个留出场景：
    training_scenes = 其余四个场景
    S = 全部 1536 个通道
    对 K = 1024, 768, 512, 384, 256, 128：
        只在 training_scenes 上评估删除 S 中每个通道的效果
        依重要性排序，保留前 K 个原始通道
        重新评估这 K 个通道组成的整体描述子在训练场景上的表现
        在留出场景评分并保存结果，该分数不反馈给本折筛选
        S = 本轮保留的通道
```

每档使用预先固定的维度预算，不会根据留出场景的分数停止、回退或改选通道。通道保留后按原始编号排序保存，因此五折的逐档通道集合都具有嵌套关系。到 1024 维时两种方法使用相同的初始排序，所以结果相同。

**384 维必须保留其前面的筛选路径。** 本报告的 384 维结果来自 `1536 -> 1024 -> 768 -> 512 -> 384`；直接用 `--dimensions 384` 会变成从完整通道排序后一步截取，不能复现本报告的逐档 384 维表现。

全维单通道消融可以逐场景独立预计算，再被不同折复用；每折汇总时只取四个训练场景。缓存复用不意味着将本折留出场景加入拟合。实现见 [channel_scan.py][scan-code] 的 `training_scene_names` 调用与逐档循环。

## 4. 比较方法与评估口径

### 4.1 对照方法

| 方法标识 | 特征变换 | 拟合使用的信息 |
|---|---|---|
| `original` | 原始 1536 维 | 无需拟合 |
| `centered_full` | 减去训练均值，保留全部 1536 维 | 四个训练场景的有效 token，用于区分中心化与降维的影响 |
| `ablation_once` | 在完整维度上排序一次，截取前 K 个原始通道 | 四个训练场景的特征与几何对应标签 |
| `ablation_iterative` | 逐档重新评估，保留 K 个原始通道 | 四个训练场景的特征与几何对应标签 |
| `random` | 固定随机排列的前 K 个原始通道 | 不依赖数据；五个固定种子；同一排列在各维度之间嵌套 |
| `pca` | 训练均值中心化后，投影到前 K 个主成分 | 四个训练场景的有效 token，不使用对应标签作排序目标 |

PCA 对每个训练场景分别计算有效 token 的均值和二阶矩，再对场景等权，得到协方差：

```text
mu = mean_over_training_scenes(mean_of_valid_tokens)
cov = mean_over_training_scenes(E[x x^T]) - mu mu^T
z_K = (x - mu) @ components[:, :K]
```

使用完整协方差特征分解，按特征值降序取主成分，不做白化。场景有效 token 数不同，不会让 token 更多的场景自动获得更大的 PCA 拟合权重。PCA 变换后的检索特征也重新做 L2 归一化。

需要注意：通道筛选利用了几何监督，PCA 和随机对照没有利用相同的监督目标。因此比较回答的是“本任务下哪一种已实现的压缩流程更有效”，不能据此推断所有 PCA 变体或其他压缩方法都不适合三维任务。

### 4.2 按场景留出，防止筛选与评分混在一起

五折中，每一折只用四个场景选择通道、计算 PCA 均值和投影；在第五个场景评分。例如，留出 `scene0707_00` 时，训练场景是 `scene0708_00`、`scene0709_00`、`scene0710_00`、`scene0711_00`。

所有维度扫描档位和随机种子在评分前已经固定。每折通道筛选不读取本折留出分数。**在看过完整扫描曲线后选择 384 维，属于本轮探索后的方案选择；对这个最终选择的独立确认仍需要新增场景。**

### 4.3 检索过程与指标

源帧某个 token 的体素在目标帧也存在时，该 token 才有可评价的对应标签。对这些查询，按余弦相似度在目标帧的**全部有效 token** 中搜索 top-1，不按真值体素或真值距离预先缩小候选集合。两个方向都检索，并在每个帧对内合并双向查询观测。

最高相似度在绝对差 `1e-6` 内的候选都视作并列，`rtol=0`。并列时，命中率按并列候选中命中的比例计分，三维误差按这些候选的距离均值计分，避免常量或重复特征通过任意索引选择获得虚假优势。

| 指标 | 定义 | 解读 |
|---|---|---|
| `retrieval_voxel_hit` | 检索结果是否与查询处于相同体素 | 越高越好；受体素网格边界影响 |
| `retrieval_hit_distance` | 检索结果与查询的世界坐标距离是否不超过 0.1 m | 越高越好；本报告称 10cm 命中率 |
| `retrieval_world_error_mean` | 双向查询的三维距离误差均值 | 越低越好，单位 m |
| `retrieval_world_error_median` | 每个帧对内双向查询误差的中位数，再按相同层级聚合 | 越低越好；汇总值不是全体查询的全局中位数 |
| `positive_similarity` | 同体素跨视角表征的相似度 | 每视角先平均该体素内的原始特征，再归一化 |
| `negative_similarity` | 不同共享体素间的相似度 | 负例距离至少 0.2 m，双向固定种子采样 |
| `similarity_gap` | 正例相似度减负例相似度 | 诊断量，不是直接的三维检索质量分数 |

正式评分全部复用 [metrics.py][metrics-code]，几何规则复用 [geometry.py][geometry-code]。筛选后 token 的归一化不能代替体素表征所需的“原始特征先平均，再归一化”。

### 4.4 汇总方式

先对每个帧对的双向可评价查询计算指标，再对场景内有效帧对等权平均，最后对五个场景等权平均。场景间和帧对间均不按查询数重新加权，所以不能直接把 14295 条查询混成一次总体命中率。

随机对照先对每个种子分别算五场景宏平均，再报告五个种子的均值。表中的 `+/-` 是这些种子宏平均值的总体标准差，不是置信区间。跨场景标准差另存在 `summary.csv`，不能与种子标准差混用。

六档维度中，三种确定性方法和五个随机种子共形成 48 个候选，加上原始与中心化对照共 50 个候选。`50 × 155 = 7750` 条帧对评分是同一批帧对上的重复比较，实际独立场景数仍然是五。

### 5.1 为什么逐档重评估重要

一次性排序和逐档剪枝在 1024 维时相同，往下压缩后逐渐分开。一次性截取到 384 维的体素命中率已经低于原始特征，继续到 256、128 维下降更大；逐档方法在这些维度上仍高于原始特征。

这说明单通道在完整 1536 维组合中的边际作用，不能直接当作大量通道同时删除后的整体效果。结果支持逐档重新评估通道间的组合关系，但不能把被删除的每个通道都认定为独立、固定的“噪声通道”，也不能据此断言找到了全局最优子集。

### 5.2 为什么不能只看相似度差或 PCA 方差

原始特征的 `similarity_gap` 为 0.0242；仅减训练均值，gap 就增至 0.3787，但体素命中率从 28.912% 降到 28.627%，10cm 命中率也下降。因此 gap 变大并不保证检索改善。

PCA 的 384 维平均保留约 94.58% 的训练协方差方差，体素命中率仍只有 27.559%。这里的方差保留率是在各折训练分布上计算的，不代表留出场景的几何判别信息保留率。保留大部分方差，也不足以保证保留对应匹配需要的信息。

## 6. 为什么以 384 维为主候选

### 6.1 相对 256、512 的具体取舍

下表是“逐档 384 维减去对照”的差值；命中率用百分点，误差用 mm，误差负值表示改善。差值均从未四舍五入的原始记录计算。

| 对照 | 维度变化 | 体素命中变化 | 10cm 命中变化 | 平均误差变化 |
|---|---|---:|---:|---:|
| 原始 1536 | 减少 75% | +2.915 | +3.685 | -24.200 |
| 逐档 256 | 增加 50% | -0.381 | +0.161 | -2.322 |
| 逐档 512 | 减少 25% | +0.238 | +0.408 | +0.646 |

如果优先考虑实际空间距离，384 维提供了当前最高的 10cm 命中率，平均误差又仅比 512 维高约 0.65 mm，同时少用 25% 的描述子维度。与 256 维相比，384 维以更多的存储和匹配维度换取略高的距离命中率和略低的平均误差。

体素命中、10cm 命中和平均误差并不等价。同体素判断受体素边界影响，10cm 命中对应固定距离阈值，平均误差还受较大误匹配距离影响。它们给出不同的最佳维度是正常现象，当前将 384 维作为质量与压缩率的折中，而不是宣称它在所有指标上都优于 256 或 512。

### 6.2 384 维相对原始特征的逐场景结果

命中率单位为 %，误差单位为 m。

| 场景 | 原始体素命中 | 384 体素命中 | 原始 10cm 命中 | 384 的 10cm 命中 | 原始平均误差 | 384 平均误差 |
|---|---:|---:|---:|---:|---:|---:|
| scene0707_00 | 36.436 | 40.420 | 55.479 | 59.275 | 0.1755 | 0.1632 |
| scene0708_00 | 33.783 | 37.724 | 39.740 | 43.275 | 0.3376 | 0.3126 |
| scene0709_00 | 35.430 | 37.455 | 50.769 | 54.429 | 0.2100 | 0.1930 |
| scene0710_00 | 24.291 | 25.241 | 42.087 | 44.787 | 0.2802 | 0.2525 |
| scene0711_00 | 14.619 | 18.291 | 29.089 | 33.824 | 0.3768 | 0.3379 |

384 维相对原始特征的三项主要几何指标在五个留出场景中均改善。相对 256 维，则有 4/5 个场景的平均误差降低、3/5 个场景的 10cm 命中率提高，体素命中率只有 1/5 个场景更高。

主要例外是 `scene0708_00`：384 相比 256 的体素命中率低 2.508 个百分点，10cm 命中率低 1.959 个百分点，平均误差高 7.463 mm。这个场景说明 384 并非对所有场景都更合适，五场景的小幅平均差异也不足以给出“稳定胜过 256”的统计结论。

### 6.3 训练表现和通道稳定性

| 方法与维度 | 四训练场景宏平均，再对折平均：体素命中率 | 留出场景宏平均：体素命中率 |
|---|---:|---:|
| 一次性 384 | 26.984% | 26.609% |
| 逐档 512 | 32.470% | 31.588% |
| 逐档 384 | 33.118% | 31.826% |
| 逐档 256 | 33.082% | 32.208% |
| 逐档 128 | 31.728% | 30.453% |

训练列使用加速 float64 检索，留出列使用原评分实现。各折训练场景相互重叠，因此训练列是诊断信息，不是额外的独立样本，也不是置信区间。

从五份实际通道列表补充计算得到：

| 保留维度 | 五折全部共同保留的通道数 | 五折通道并集大小 | 十对折间平均 Jaccard |
|---|---:|---:|---:|
| 256 | 2 | 785 | 0.1465 |
| 384 | 7 | 977 | 0.2263 |
| 512 | 33 | 1126 | 0.3002 |

Jaccard 定义为两个通道集合的交集大小除以并集大小。即便 384 维在所有留出场景上都优于原始特征，各折选出的具体通道仍有较大差异。这支持“筛选流程有效”的结论，尚不能将其中任意一折的列表当作已经证明通用的一份固定 mask。

## 7. 正确性检查与限制

### 7.1 已完成的检查

- 正式实验前复算原始 155 个帧对。七项原有指标的最大绝对差均为零；允许阈值为 `1e-6`。见 [baseline_check.json][baseline-check]。
- 通道消融与已有几何测试共 26 项通过，包括真实切片与加速删除的一致性、常量/全零/稀疏特征、分数化并列、合成干扰通道、PCA 留出隔离、场景等权、缺失帧对及随机种子波动的汇总。
- 全部 7750 条候选评分具有与原始特征相同的有效 token 数、共享体素数、可评价查询数、负例数量和缺失状态。
- 检查五折训练场景隔离、PCA 拟合场景、通道编号范围、通道数、排序和逐档集合嵌套。
- 最终版本完整运行成功；汇总结果与首次完整评分完全一致，运行时记录的代码哈希与对应源文件一致。见 [audit.json][audit]。

最后一次完整执行记录约 318.51 秒，PyTorch 峰值已分配 GPU 内存约 607.65 MiB，使用 `cuda:6`。这不包括此前的 Wan 特征提取，也不是下游应用的延迟或显存基准。CUDA 上下文、缓存预留和设备总占用也不能直接用该数字代替。

### 7.2 仍需验证的部分

本次是五个场景、单一 block、单一噪声设置下的相邻采样帧探针，不是 ScanNet 全部场景或所有跨视角帧对的完整基准。14×14 池化后的世界坐标是有效投影点的平均，在边界等位置存在近似；小于毫米级的方案差异尤其不应被过度解释。

384 维的选择发生在看到本轮维度曲线之后。下一步应固定筛选流程和 384 维目标，用现有训练场景拟合一份通道列表，再到额外场景检验；256 维保留为压缩率对照。该固定列表的额外场景验证尚未完成。

裁剪的是输出描述子通道。384 维描述子在相同数据类型下的元素数和存储量是 1536 维的四分之一，通道相关的匹配计算量也随之减少；本轮没有测量端到端加速，更没有减少 Wan 内部完整 B15 前向的计算或模型权重。

### 8.3 完整实验的复现命令

在仓库根目录执行，需先准备原始基线结果 `../eval/scannet/07c02b354a694662` 和对应的 `../cache/scannet/` 几何、特征缓存。显式设置源码路径，防止恢复后的 editable 安装指向历史 checkout；示例设备是本次记录使用的设备，换设备或其他配置会生成新的运行身份。重新提取缓存的方法见 [ScanNet 运行说明](../../../scripts/scannet/README.md)；其他基线运行目录通过 `--baseline-run` 指定。

```bash
export PYTHONPATH="$PWD/src:$PWD/diffusers/src"
```

### 8.4 如何使用已保存的 384 维通道列表

以下示例从仓库根目录读取随报告上传的某一折通道列表，不代表已额外验证的全场景通用 mask。`hidden` 应为相同提取流程得到的 `[B, 1536, 14, 14]` 张量。

```python
import json
from pathlib import Path
import torch
import torch.nn.functional as F

fold_dir = Path(
    'reports/scannet_channels/ef4d46fa8afe1019/'
    'results/folds/scene0707_00'
)
masks = json.loads((fold_dir / 'masks.json').read_text())
indices = torch.tensor(
    masks['ablation_iterative_384'], dtype=torch.long, device=hidden.device
)
selected_raw = hidden.index_select(1, indices).float()
retrieval_descriptors = F.normalize(selected_raw, dim=1, eps=1e-12)
```

`selected_raw` 保留裁剪后的原始特征，供需要先按体素平均再归一化的统计使用；`retrieval_descriptors` 是逐 token 归一化的匹配描述子。正式复现本报告时，仍应将原始裁剪特征送入原有 `evaluate_pair`，由其执行完整评分协议。
